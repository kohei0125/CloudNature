# 10. 推奨構成

## 導入
- ChatGPTにプロンプトを送るだけならエージェントではない
- 実務で価値が出るのは、情報取得、判断、ツール実行、結果確認まで一連の流れを設計したとき
- ただし自律性を高めるほど、権限と事故時の影響も増える

## H2 AIエージェントとは
LLMアプリ、チャットボット、RPA、ワークフローとの違い。厳密な境界が業界で完全統一されているとは書かない。

## H2 AIエージェントを作る前に「業務」を選ぶ
業務選定チェック:
- 入力がある程度定義できる
- 出力を人間が評価できる
- 必要なデータへアクセスできる
- 一定頻度で繰り返される
- ミスした場合の影響を限定できる
- 自動化による価値が測定できる

## H2 AIエージェントの基本構成
図解: ユーザー/トリガー → モデル → 指示・ルール → データ参照 → ツール → 状態管理 → 人間承認 → 実行結果 → ログ・評価

## H2 作り方7ステップ
1. 対象業務と成功条件を決める
2. 入力・出力・例外条件を定義する
3. 必要なデータとツールを洗い出す
4. 権限と人間承認を設計する
5. 実装方式を選ぶ
6. 小さくPoCする
7. ログ・評価をもとに本番化する

## H2 実装方式の比較
「万能ランキング」にしない。用途ごとに分類する。
- SaaS内のAI機能
- ノーコード／ローコードのワークフロー型
- AIエージェントフレームワーク
- 独自アプリケーション＋LLM API

Dify、n8n、Google ADK、Mastra等は執筆時点の公式仕様を調べ、どの分類に置くかを説明。
「どれが一番」ではなく、権限、複雑さ、保守性、既存システムとの関係で選ぶ。

※ この章に `/services/ai-agent` への内部リンクを置く（補正1）。

## H2 MCP・A2A（必要な場合のみ簡潔に）
- MCP: モデルやAIアプリから外部のツール・データにアクセスするための標準化された接続方法
- A2A: エージェント間連携を扱う文脈

公式仕様を確認し、2026年時点の最新定義に従う。この記事の主役にしない。

## H2 AIエージェントに向かない業務 ★この記事で最も差別化できる章

**独立H2で必ず入れる。AIに書かせると必ず薄くなる箇所なので、以下の枠組みを使って厚く書く。**

業務を「定型／非定型」×「単純／創造的」の4象限で分類する。

| | 単純 | 創造的 |
|---|---|---|
| **定型（ルール明確）** | ❌ 生成AIは不向き。ルールベースの自動化（プログラミング・Excel・RPA）で対応 | ⚡ 生成AIを含む自動化ワークフロー |
| **非定型（ルール不明確）** | 👤 人間が残る仕事（スポットで突発的に入る単純作業） | 🤖 生成AIをパートナーとして活用 |

ここから導く重要な示唆:
- **「めんどくさい単純作業をAIにやらせたい」は実は生成AIが向いていない。** 毎回同じ結果が必要な処理は、出力が変わりうるLLMより決定論的な処理のほうが適切
- 人間がこれまで価値があると思っていた高度な判断作業こそ、生成AIが力を発揮する領域
- PDCAで言えば、生成AIが得意なのは **P（計画）・C（評価）・A（改善）** であり、**D（実行）の自動化は従来型の自動化**が向く

その他の向かないケース:
- ミスが即重大事故につながり、人間承認を挟めない処理
- 入力・判断基準が全く定義できない業務
- 自動化頻度が低くROIが合わない業務
- 必要なデータへのアクセス権を整理できない業務

**「AIエージェントより普通のプログラム/RPAの方が良いケースがある」と明言する。**
競合記事はほぼ全てAIエージェントを万能に書いており、そこが逆に信用を落としている。ここが勝ち筋。

## H2 セキュリティ
抽象的な「安全です」で終わらせない。最低限:
最小権限／読み取りと書き込みの分離／Secret管理／個人情報・機密情報の扱い／監査ログ／外部API送信データ／人間承認／Prompt Injection等のエージェント特有リスク

技術対策は公式セキュリティ資料を根拠にする。

## H2 PoCと評価
「動いたから成功」にしない。評価軸の例:
タスク成功率／人による修正率／処理時間／失敗率／誤操作数／1件あたりコスト／人間へのエスカレーション率

数値の合格ラインは業務ごとに設定するため、一般的な正解値を捏造しない。
